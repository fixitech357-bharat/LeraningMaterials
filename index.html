00 — CONTEXT

Why Security Is Changing in 2026

Three forces are reshaping application security. Understanding them is the difference between building software that survives and software that becomes a headline.

1. AI-Assisted Development at Scale AI agents now generate, review, and deploy code. This accelerates development but introduces new attack surfaces — prompt injection, excessive agent permissions, and AI-generated vulnerabilities.
2. Identity Everywhere Applications no longer serve only humans. They serve services, workloads, bots, and AI agents. Every entity needs an identity, authentication method, and authorization policy.
3. Zero Trust as Default Perimeter security is dead. Modern architectures assume breach, verify everything, and enforce least privilege at every layer.

These shifts demand that developers understand security deeply — not as an afterthought, but as a core engineering competency.

03 — MODERN AUTHENTICATION

Modern Authentication

Authentication Methods Compared

MethodHow It WorksSecurityUser Experience
PasswordShared secretLowFamiliar but friction-heavy
OTPOne-time code via SMS/email/appMediumAdds step, SMS is weak
MFAMultiple factors combinedHighSlightly more friction
BiometricsFingerprint, face, voiceHighSeamless on devices
SSOSingle login for multiple appsHighExcellent

PasskeysFIDO2 / WebAuthn credentialsVery HighBest UX + security

Password vs OTP vs MFA vs Passkeys

PasswordSomething you know. Vulnerable to phishing, reuse, brute force. Requires hashing, salting, complexity rules.
OTPSomething you have (temporarily). SMS OTP is vulnerable to SIM swapping. App-based (TOTP) is stronger.
MFACombines multiple factors. Something you know + something you have. Significantly reduces account takeover.
PasskeysBased on FIDO2/WebAuthn. Private key stored on device, never transmitted. Phishing-resistant by design.

Why Passwordless Is the Future

Passwords are reused across services, phished easily, stored insecurely, and forgotten constantly.

Passkeys solve these problems:

Phishing-resistantNo secret to steal.
No reuseUnique per service.
No breach riskPrivate key never leaves the device.
Better UXBiometric or PIN unlock.

Major platforms (Apple, Google, Microsoft) now support passkeys natively.

FIDO2, WebAuthn, and Security Keys

FIDO2 is the standard for passwordless authentication. WebAuthn is the web API implementing FIDO2. Security keys (hardware tokens) provide the highest assurance — physical possession required.

1. User registers device with service
↓
2. Service stores public key
↓
3. User signs challenge with private key
↓
4. Service verifies signature

No shared secret. No phishing risk.

Device Authentication

Devices can also be authenticated: device certificates, TPM-backed keys, device fingerprinting, MDM enrollment. This enables device-aware access — only trusted devices can access sensitive resources.

04 — AUTHORIZATION MODELS

Authorization Models

Authorization determines what an authenticated identity can do.

ModelHow It WorksExampleBest Use Case

PBACPolicies define access"Managers can approve expenses < $5000"Business rule-heavy systems

ACLPer-resource permission listsFile shared with specific usersDocument management

RBAC (Role-Based Access Control)

Users are assigned roles. Roles have permissions.

User
→
Role
→
Permissions
→
Resources

Example: Alice has role "Editor". Editor can read, write, update articles. Therefore Alice can edit articles.

Pros: Simple, scalable for basic hierarchies. Cons: Role explosion in complex systems.

ABAC (Attribute-Based Access Control)

Access decisions based on attributes of user, resource, action, and environment.

IF user.department == "Finance"
AND resource.classification <= "Confidential"
AND time.hour BETWEEN 9 AND 17
THEN allow access

Pros: Highly flexible, context-aware. Cons: Complex to manage.

PBAC (Policy-Based Access Control)

Centralized policies define access rules.

{
  "effect": "allow",
  "action": "read",
  "resource": "document:*",
  "condition": {
    "user.clearance": { "gte": 3 }
  }
}

ReBAC (Relationship-Based Access Control)

Access based on relationships between entities. Used by Google (Zanzibar) and in collaborative apps.

Example: User is member of Project X. Project X has document Y. Therefore, user can access document Y.

Least Privilege

Principle: Grant only the minimum permissions necessary. Start with no access, add permissions explicitly, review regularly, remove unused permissions. Why it matters: It limits the blast radius of compromised accounts.

06 — JWT + TOKENS

JWT + Tokens

JWT Structure

A JWT has three parts, base64-encoded and dot-separated:

header.payload.signature

Header

{ "alg": "RS256", "typ": "JWT" }

Payload

{ "sub": "user123", "role": "admin", "exp": 1735689600 }

Signature

RSASHA256(base64(header) + "." + base64(payload), privateKey)

When JWT Is Useful

Stateless authenticationNo server-side session store.
API authorizationCarry claims directly in the token.
Single sign-onAcross multiple services.
MicroservicesService-to-service communication.

Common JWT Mistakes

Common Web Attacks

CORS (Cross-Origin Resource Sharing)

Controls which origins can access your API from browsers. Misconfiguration risk: Access-Control-Allow-Origin: * with credentials. Fix: Explicitly list allowed origins.

CSRF (Cross-Site Request Forgery)

Attacker tricks user's browser into making requests. Prevention: CSRF tokens, SameSite cookies, origin validation.

XSS (Cross-Site Scripting)

Attacker injects malicious scripts. Types: Stored, Reflected, DOM-based. Prevention: Output encoding, Content-Security-Policy, input validation, framework auto-escaping.

SQL Injection

Attacker injects SQL via user input.

SELECT * FROM users WHERE name = '${input}'

Input: ' OR '1'='1 — Prevention: Parameterized queries, ORMs, input validation.

SSRF (Server-Side Request Forgery)

Attacker tricks server into making requests to internal resources. Prevention: Allowlist destinations, block internal IPs, validate URLs.

Clickjacking

Attacker embeds your site in an iframe to trick clicks. Prevention: X-Frame-Options: DENY, Content-Security-Policy: frame-ancestors 'none'.

09 — ENCRYPTION & PASSWORD SECURITY

Encryption & Password Security

Encryption vs Hashing vs Encoding

OperationReversible?Purpose
EncryptionYes (with key)Confidentiality
HashingNoIntegrity, password storage
EncodingYes (trivially)Data format conversion

Symmetric vs Asymmetric Encryption

TypeKeyExampleUse Case
SymmetricSame keyAESData at rest, bulk encryption
AsymmetricPublic/private pairRSA, ECCKey exchange, signatures

Digital Signatures, TLS & PKI

Sign with private key, verify with public key. Provides authenticity, integrity, and non-repudiation.

TLS uses asymmetric crypto to establish symmetric session keys. PKI (Public Key Infrastructure) manages certificates and trust. Certificates bind public keys to identities, signed by CAs.

Why Passwords Should Be Hashed, Not Encrypted

Encryption is reversible. If the key leaks, every password is exposed. Hashing is one-way. Even with the hash, you can't recover the password.

bcryptAdaptive, widely used, tunable cost factor.
Argon2Winner of the Password Hashing Competition. Memory-hard.

Never use MD5, SHA-1, or SHA-256 alone for passwords.

Secrets Management

Never hardcode secrets. Use environment variables, secret managers (Vault, AWS Secrets Manager), or encrypted Kubernetes secrets. Rotate secrets regularly. Audit access.

10 — OWASP TOP 10

OWASP Top 10 — Developer Perspective

Click each item to expand: what it means, a simple example, why it happens, and how to prevent it.

A01Broken Access Control▼

What: Users can access resources they shouldn't.

Example: Changing /user/123 to /user/124 exposes another user's data.

Why: Missing server-side authorization checks.

Prevention: Enforce authorization server-side. Deny by default.

A02Cryptographic Failures▼

What: Weak or missing encryption.

Example: Storing passwords in plaintext.

Why: Misunderstanding crypto, legacy systems.

Prevention: Use strong algorithms. Hash passwords. Encrypt sensitive data.

A03Injection▼

What: Untrusted data interpreted as code.

Example: SQL injection, command injection.

Why: Concatenating user input into queries.

Prevention: Parameterized queries. Input validation. Least privilege.

A04Insecure Design▼

What: Flaws in architecture, not implementation.

Example: No rate limiting on password reset.

Why: Security not considered during design.

Prevention: Threat modeling. Secure design patterns.

A05Security Misconfiguration▼

What: Insecure default settings.

Example: Debug mode in production. Open S3 buckets.

Why: Oversight, lack of hardening.

Prevention: Secure defaults. Regular audits. Automate configuration.

A06Vulnerable Components▼

What: Using libraries with known vulnerabilities.

Example: Outdated Log4j.

Why: Not tracking dependencies.

Prevention: Dependency scanning. Regular updates. SBOM.

A07Identification & Authentication Failures▼

What: Weak authentication mechanisms.

Example: No MFA. Weak password policies.

Why: Convenience over security.

Prevention: MFA. Strong password hashing. Session management.

A08Software & Data Integrity Failures▼

What: Trusting unverified code or data.

Example: Insecure deserialization. Unsigned updates.

Why: No integrity verification.

Prevention: Sign artifacts. Verify checksums. Use trusted sources.

A09Security Logging & Monitoring Failures▼

What: Not detecting or responding to breaches.

Example: No logs of failed logins.

Why: Logging overlooked.

Prevention: Log security events. Monitor. Alert. Respond.

A10SSRF▼

What: Server makes requests to attacker-controlled destinations.

Example: Fetching internal metadata service.

Why: Unvalidated URLs.

Prevention: Allowlist. Block internal IPs.
